## 0. 结论摘要

1. **功能不缺，缺的是收敛**。全局跨会话正文检索（FTS5）、批量迁移/删除、子代理折叠、token 统计都已在代码里跑通；问题集中在呈现层与工程形态。
2. **同一套界面存在两份实现**。`web_app.py` 里 `HTML_PAGE`（4117–9794 行，约 5,676 行内嵌 HTML/CSS/JS，另内联 `marked.min.js` 39KB）与 `frontend/`（22 个文件、3,832 行 Next.js）并行维护。用户说的"改来改去都改乱了"和"面板 AI 味仍太重"，根源在这两份实现交替覆盖。
3. **"毫秒级"类话术在旧实现里仍然活着**。新前端已清干净，但 `HTML_PAGE` 第 9668、9784 行仍写着"毫秒级全文精确检索与高亮定位"，`#2` 的整改没有完成闭环。
4. **缓存设计是当前体验的瓶颈**。后端会话列表缓存 TTL 仅 4 秒且失效即全量重算（逐文件 stat + 逐个 Antigravity `.db` 查 steps 计数 + 逐会话算 token），`next.config.ts` 注释自述"全量扫描 348 篇会话约需 30s"；同时前端 `api/client.ts` 写死 `cache: 'no-store'`，把后端已有的 ETag/304 能力直接关掉。
5. **两个进程不是"前后端分离"的必要条件**。前端全部数据走 `/api` 客户端请求，没有任何 SSR 取数；`output: 'export'` 即可由 18922 单端口直接托管，`next.config.ts` 里的 `proxyTimeout: 180_000` 这类补丁和"杀 3000 端口"的脚本逻辑可以一起消失。

## 3. 优化 PRD（增量）

三个方向来自用户点名的诉求：现代化架构（#16）、缓存与数据管理（#10、#12）、前后端分离（#10、#16、#17）。**不在本次范围**：新增数据源平台、云端同步、多人协作、移动端原生 App。

### 方向 A · 现代化架构

#### A-1（P0）退役内嵌前端，只保留一份前端实现

- **问题**：`HTML_PAGE`（4117–9794 行）与 `frontend/` 两套界面并存，交替覆盖同一批交互，是"改乱了"和"AI 味复活"的直接原因；`marked.min.js` 仅为旧页存在。
- **目标**：任何界面改动只有一处落点；`web_app.py` 退回纯 API 服务。
- **验收标准**：
  1. `web_app.py` 内不再出现 `HTML_PAGE`、`<style`、`<script` 与内联 JS 字符串；
  2. 访问 `/` 由前端产物（或其重定向）接管，页面内容与新前端一致；
  3. 全局检索"毫秒级"零命中（UX-01 闭环）；
  4. `marked.min.js` 从仓库移除或移入归档目录，构建不再引用。
- **不做什么**：不顺手重排视觉；不借机改接口路径；不为"兼容旧书签"保留旧页。

#### A-2（P0）后端按职责拆分，保持单进程与契约不变

- **问题**：9,852 行单文件里混着 protobuf 解析、token 估算、FTS 索引、HTTP 分发、模板字符串，无法独立测试任一层。
- **目标**：拆成可单测的模块，对外 HTTP 契约零变更。
- **验收标准**：
  1. 至少分出：`server`（路由与响应）、`platforms`（各平台解析）、`tokens`、`search`（FTS）、`catalog`；
  2. 现有 13 个接口（GET 5 个 + POST 8 个）的路径、入参、返回结构逐字段不变（用改造前的响应快照做契约比对）；
  3. 各模块可脱离 HTTP 单独调用并有最低限度用例；
  4. 仍是一个进程、一个端口启动。
- **不做什么**：不引入 Web 框架重写路由（`http.server` 够用）；不改数据目录结构；不迁移到异步框架。

#### A-3（P1）建立质量门槛，对齐参照项目的工程基线

- **问题**：`#7`/`#13`/`#16` 要求"浏览器实测、多尺寸验证"，当前无 lint、无类型检查脚本、无 e2e，验证靠人眼，回归不可复现。
- **目标**：主路径可一键验证。
- **验收标准**：
  1. `lint`、`typecheck`、`test:e2e` 三个脚本可用，任一项失败即视为不可交付；
  2. e2e 覆盖：列表加载与筛选 → 打开详情（含 Markdown 样例） → 全局检索并跳转轮次 → 批量删除 → 迁移弹窗；
  3. 至少 3 个视口（360 / 768 / 1440）在 e2e 中断言无横向滚动。
- **不做什么**：不追求覆盖率数字；不做视觉回归基线库；不为测试引入第二套构建工具。

#### A-4（P2）设计 tokens 收口

- **问题**：StyleKit 体系已移植，组件层硬编码已很少（`BatchManagementDrawer.tsx:374` 一处 hex，`globals.css` 4 处深色主题覆盖），但没有可核对的 token 清单，这 5 处取值也没有归属说明，`UX-02` 无法核对。
- **目标**：颜色、间距、字号、圆角、阴影五个维度的取值全部来自 tokens。
- **验收标准**：`tailwind.config.ts` + `globals.css` 导出一份 token 清单；组件内无裸色值（`#xxxxxx`）与魔法间距（除 0/1px 外）。
- **不做什么**：不重做视觉稿；不因 token 化调整任何现有尺寸观感。

### 方向 B · 缓存与数据管理

#### B-1（P0）会话列表缓存改为内容指纹驱动，去掉 4 秒 TTL

- **问题**：`handle_get_sessions` 的缓存窗口只有 4 秒（`_GLOBAL_SESSIONS_CACHE`），过期即重跑 `collect_all_sessions()`：逐文件 `stat`、逐个 Antigravity `.db` 查 `steps` 计数、逐会话算 token。`next.config.ts` 注释自述全量约 30s，这就是"每次打开都转圈"的来处。
- **目标**：列表响应在数据未变时不做重算，冷启动与热启动成本可预期。
- **验收标准**：
  1. 数据未变时连续 10 次请求，第 2 次起总耗时 ≤ 200ms（不含首次索引）；
  2. 缓存键包含目录根集合 + 各文件 `mtime`/`size` 指纹，任一文件变动只影响该条；
  3. 会话列表规模 3 倍于当前（约 1,000 条）时，热请求仍 ≤ 500ms；
  4. 缓存可持久化到 `catalog.sqlite3` 侧表，重启进程后首次响应不触发全量重算。
- **不做什么**：不改会话卡片展示字段；不为提速删减 token 统计口径；不做跨机器缓存共享。

#### B-2（P0）启用 ETag/304，前端不再主动禁用 HTTP 缓存

- **问题**：后端每份 JSON 都带 ETag 并支持 304（`_send_compressed`），但 `api/client.ts` 写死 `cache: 'no-store'`，该能力形同废弃；每次切筛选都重传全量 payload。
- **目标**：复用已有 ETag，重复请求走 304 空响应体。
- **验收标准**：
  1. 相同参数的第二次请求返回 304，网络面板响应体接近 0 字节；
  2. 数据变更（`dataVersion` 自增）后请求返回 200 且内容更新；
  3. 列表刷新时界面保留旧数据并展示加载态，不出现空白闪烁。
- **不做什么**：不引入 Service Worker；不改 SWR 的调用位置；不做离线优先。

#### B-3（P1）全文索引的体积与增量治理

- **问题**：`dialogue_fts.sqlite3` 实测 71.7MB，对应 328 个文件 / 26,929 轮对话，折算单轮索引开销约 2.7KB；`cjk_tokenize` 按字切分写索引，中文语料下体积膨胀是主因。另有 `-wal` 2.3MB 常驻，说明检查点不频繁。`index_session_turns` 对已变更会话是整条 `DELETE` 再全量插入，长会话反复重建成本高。
- **目标**：索引体积与增量同步成本可控，且检索结果不退化。
- **验收标准**：
  1. 同等语料下索引体积下降 ≥ 30%，`UX-01`/`FR-05` 口径下的检索结果集不变（用固定查询集比对命中条数与排序）；
  2. 单篇会话变更时只重建该篇，且耗时不随库内总会话数线性增长；
  3. 界面可显示索引库体积（FR-05）；
  4. 明确边界：会话数 1,000 / 索引 30 万轮时，单次查询 ≤ 300ms。
- **不做什么**：不引入 Elasticsearch / Meilisearch 等外部服务（本地工具不应多一个守护进程）；不改 FTS5 之外的检索依赖。

#### B-4（P1）列表分页或窗口化，停止全量返回

- **问题**：`handle_get_sessions` 无分页，每次都返回全量会话（含 `file_path`、token 字段等约 20 个字段）；当前 348 条尚可，量级上升后前后端一起变慢。
- **目标**：首屏只传可视窗口所需数据，滚动再取。
- **验收标准**：首屏请求返回条数 ≤ 60；滚动到底部按页追加；排序与筛选在服务端完成且结果与全量模式一致。
- **不做什么**：不改排序字段语义；不为了分页牺牲"折叠同源分叉"的跨页一致性（分叉判断需在服务端完成）。

#### B-5（P2）token 计算成本治理

- **问题**：`compute_session_tokens` 在列表聚合阶段逐会话参与计算，`token_cache.json`（107KB）已做持久化，但缓存键与失效策略未文档化，改动解析逻辑后可能读到旧值。
- **目标**：token 数值可追溯、缓存失效有明确规则。
- **验收标准**：缓存键含解析器版本号；解析逻辑变化自动失效；界面标注该会话 token 是"客户端记录"还是"tiktoken 估算"。
- **不做什么**：不改计费口径；不引入新的 tokenizer 依赖。

### 方向 C · 前后端分离

**先明确判据**：分离指"源码、依赖、构建"三层解耦，前后端只通过 HTTP 契约通信；**不等于**运行时必须两个进程。本机单用户工具，多一个监听端口就多一处故障面。

#### C-1（P0）前端改为静态产物，由后端起单端口服务

- **问题**：现在必须同时跑 18922（Python）与 3000（Next.js server）。由此产生三层补丁：`next.config.ts` 的 `rewrites` 代理、`proxyTimeout: 180_000`（注释自述是为绕开 30s 代理断开）、启动脚本与 `.vbs` 里的端口双杀逻辑。用户 `#17`/`#18` 的启动困扰正是这套结构的衍生成本。
- **目标**：一个进程、一个端口（18922）即可完整使用；前端仍保有独立的构建流程与依赖树。
- **验收标准**：
  1. 前端以静态导出方式构建（`output: 'export'` 或等价方案），产物由后端静态托管；
  2. 停止运行 3000 端口后，界面全部功能可用（含检索、迁移、批量操作）；
  3. `next.config.ts` 不再有 `rewrites` 与 `proxyTimeout`；启动脚本不含 `npm/pnpm run start`；
  4. 冷启动到可交互 ≤ 5s（不含首次索引）。
- **不做什么**：不重写成 Vite（现有 App Router 目录与组件不动，只改输出模式）；不引入反向代理；不改 API 契约；不为了单端口牺牲前端独立部署能力（保留一条"仅构建前端"的命令）。

#### C-2（P1）契约固化与契约测试

- **问题**：`api/normalize.ts`（159 行）手写适配后端字段，后端字段一改前端静默降级为空值；`normalize` 的存在本身说明契约没有权威定义。
- **目标**：后端返回结构有唯一事实来源，字段变更能立刻失败。
- **验收标准**：
  1. 每个接口有 schema 定义（手写类型 + 运行时校验任一方案）；
  2. 契约测试用真实响应样本跑通，字段缺失或类型变化即报错；
  3. `normalize.ts` 只保留"兼容旧版本"的最小逻辑，不作为主要适配层。
- **不做什么**：不引入 gRPC / GraphQL；不做接口版本号体系（本地工具无多客户端）。

#### C-3（P2）本地接口收敛暴露面

- **问题**：`main()` 第 9824 行 `server_address = ("0.0.0.0", PORT)` 监听全部网卡，而同网段任何设备调用 `/api/sessions/batch_delete` 都会被无条件执行；响应头又固定带 `Access-Control-Allow-Origin: *`，浏览器里任意网页也能跨源发起写请求。当前删除/迁移类接口没有任何来源校验。
- **目标**：只有本机、只有本工具的前端能调用写接口。
- **验收标准**：
  1. 默认仅绑定 `127.0.0.1`；需要真机调试时用显式开关临时放开，并在界面标出"当前对局域网开放"；
  2. 写接口（delete / batch_delete / migrate / catalog 变更）校验来源；
  3. 跨源请求被拒绝后界面给出可读提示，而非静默失败。
- **不做什么**：不加登录体系；不做多用户权限模型。

### 优先级汇总

| 优先级 | 条目 | 理由 |
|---|---|---|
| P0 | A-1、A-2、B-1、B-2、C-1 | 直接决定"改乱了""转圈""启动报错"三件事能否一次收口；且互相依赖（A-1 完成后 C-1 才有意义） |
| P1 | A-3、B-3、B-4、C-2 | 决定后续迭代是否可持续、数据量增大会不会塌 |
| P2 | A-4、B-5、C-3 | 体验与安全的收尾项，可在 P0/P1 稳定后做 |

### 建议实施顺序

`A-1（退役内嵌页）` → `C-1（单端口）` → `B-2（ETag）` → `B-1（缓存指纹）` → `A-2（后端拆分）` → `A-3（质量门槛）` → 其余。
前四步可在一次改动内完成并验证，因为它们共用同一条请求链路；`A-2` 放在功能验证通过之后，避免拆分期间行为漂移。
